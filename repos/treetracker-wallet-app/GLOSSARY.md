## Domains

### Wallet Management

Handles the lifecycle of a user's token wallet: creating a wallet, listing and viewing wallets and their balances, and updating a wallet's profile. It also covers the event-driven automatic provisioning of a wallet when a new user account is created.

**Terms:** Wallet, Wallet Profile

**Rules:**

- A wallet has a unique display name, checked for duplicates before creation.
- New user accounts are auto-provisioned a wallet via an event-driven queue, not a direct API call from signup.
- Wallet profile updates support optional logo and cover image uploads via multipart PATCH.

**Flows:**

- **Create Wallet** (`User taps or clicks Create Wallet in the wallet list UI (web or native)`): A user creates a new token wallet from the web or native app, with a duplicate-name check and optional redemption of a pending shared action token immediately after creation.
- **View and Update Wallet** (`User opens the Wallets list or a specific wallet`): A user lists their wallets, opens a wallet to see its balance and details, and can update the wallet's profile (name, about text, visibility, images).
- **Automatic Wallet Provisioning** (`Postgres NOTIFY on the wallets/creation channel, published after a new Keycloak account is created`): When a new user account is created in Authentication & Identity, the backend listens for a queue notification and automatically creates a wallet for the new account, decoupling registration from wallet setup.

### Token Transfer

Governs how tree-planting tokens move between wallets: initiating direct or link-shared transfers, responding to incoming transfer notifications, cancelling outgoing transfers, and viewing transfer and token history.

**Terms:** Transfer, Token, Action Token, Notification

**Rules:**

- A transfer moves either a bundle of generic tokens or a specific set of token ids from one wallet to another.
- Pending incoming transfers are surfaced as notifications until the recipient accepts or declines them.
- Only the sender can cancel a still-pending outgoing transfer.
- Action tokens are signed, time-limited credentials that let a transfer be completed via a shareable link instead of a direct recipient wallet.

**Flows:**

- **Send Transfer** (`User opens the Send page/screen`): A user selects a sending wallet, chooses or searches for a recipient, enters an amount and note, optionally generates a shareable claim link, and submits the transfer.
- **Share Token via Link** (`Sender generates a shareable claim link; recipient opens /claim`): A sender shares tokens with someone who may not yet have an account: an action token is generated, embedded in a claim link, and redeemed by the recipient after they register and create their first wallet.
- **View and Respond to Transfer Notifications** (`User opens the Notifications list`): Pending incoming transfers appear as notifications; the recipient opens a notification's detail to accept the transfer and receive the token, or decline it.
- **Cancel Transfer** (`User opens Transfers list and selects a pending outgoing transfer`): A sender views their outgoing pending transfers and cancels one before the recipient responds.
- **View Transfer and Token History** (`User opens Transfers or Token details page`): A user browses their transfer history and drills into a specific transfer or token to see its details and transaction lineage.

### Search & Discovery

Lets users find wallets, most often to choose a recipient for a token transfer, by typing a query or displaying a scannable QR code that others can search for.

**Terms:** Search Result, Wallet (as search target)

**Rules:**

- Search results are sectioned into matching, non-matching, or category-grouped results with computed relevance sorting.
- A wallet's QR code is a shareable identifier that lets other users find and select it via search.

**Flows:**

- **Search Wallets** (`User types in the header/search screen search box`): A user types a query in the search box; the app derives sectioned, category-grouped results and lets the user open a wallet's details.
- **Display Wallet QR Code** (`User opens their wallet's QR code display`): A user displays their own wallet's QR code so another user can scan or search for it as a transfer recipient.

### Authentication & Identity

Manages user registration, login, session token lifecycle, and logout, all delegated to a centralized Keycloak identity provider, plus the backend's own service-account credentials for calling Keycloak's admin API.

**Terms:** User Account, Session Token, Service-Account Token

**Rules:**

- User registration and login are delegated to a hosted Keycloak instance rather than handled with local credential storage.
- The backend caches a single service-account token, refreshing it only when missing or expired, to call Keycloak's admin API.
- Session tokens are persisted through a cross-platform storage adapter: session storage on web, AsyncStorage on native.

**Flows:**

- **User Registration** (`POST /api/auth/signup (web) or Keycloak hosted registration redirect`): A new user registers via Keycloak's hosted registration page or an in-app form; the backend creates the account in Keycloak and a wallet-creation event is published for downstream provisioning.
- **User Login** (`POST /api/auth/login (web) or Keycloak hosted login redirect`): A user logs in via Keycloak's hosted login page or an in-app form, and the app handles the resulting OIDC callback.
- **Session Token Management** (`App mount / KeycloakProvider initialization`): The app initializes the Keycloak client on mount, mirrors and persists the resulting token, keeps it refreshed, and clears it on logout.
- **Backend Service-to-Service Auth** (`Backend service needs a Keycloak service-account token to call an admin API`): The backend obtains and caches its own Keycloak service-account token via the client-credentials flow so it can call Keycloak's admin API on behalf of users.
